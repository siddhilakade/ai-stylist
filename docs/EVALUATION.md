## Why these metrics

Precision, recall and NDCG all require per-query relevance labels. There is no ground truth for *outfit compatibility* on this catalog, and authoring one by hand would mean grading the system against its own rules. Rather than report a fabricated NDCG, the evaluation measures properties that are objectively checkable: does the system obey the constraints it was given, does it stay inside the budget, does it return real products, and does it fail usefully when it cannot succeed.

## Findings — where the system disagreed with the reviewer

Expectations were written before the first run and have **not** been edited to match the results. Each disagreement was inspected and adjudicated; the adjudication is recorded below verbatim from `data/eval_scenarios.json`.

**S07** (`formal`) — expected *failure*, got *success*.  
Request: “Corporate formal wear for a woman, budget 9000.”  
Adjudication: EXPECTATION WAS WRONG. The system succeeds. Stratified sampling deliberately over-sampled the sparse women's-formal cell, and the wider accessory formality band supplies belts and watches, so a complete look is assembled. Inspected manually: the outfits are genuinely office-appropriate. Left as a failure expectation so the record shows the sparse cell was tested.

**S15** (`ethnic`) — expected *failure*, got *success*.  
Request: “Kurta based festive look for men, budget 7000.”  
Adjudication: EXPECTATION WAS WRONG. The system succeeds because the 'must be ethnic' rule is enforced only on top/bottom/one-piece, and men's ethnic bottoms do exist in the sampled catalog. Manual check: the kurta pairings are reasonable.

**S21** (`sparse_or_conflicting`) — expected *failure*, got *success*.  
Request: “Formal gym outfit for men, 5000.”  
Adjudication: GENUINE DEFECT, NOW FIXED. The system silently honoured the stated style and returned formalwear with no indication that the request was contradictory. Added `recommender.detect_conflicts`, which now flags the clash in the UI while still returning a best-effort result. Outcome stays 'success' by design - refusing to answer would be worse UX than answering with a visible warning.

**S22** (`sparse_or_conflicting`) — expected *failure*, got *success*.  
Request: “Ethnic formal office wear for women, 8000.”  
Adjudication: EXPECTATION WAS WRONG, AND THE SYSTEM IS RIGHT. Ethnic officewear is entirely normal in India - a kurta to work is not a contradiction. The exclusion rule only applies when the user did NOT ask for ethnic. A conflict notice is still shown, which is the correct amount of caution.

## Known limitations of this evaluation

- **No relevance ground truth.** Everything above measures constraint
  satisfaction, not whether a human would call the outfit stylish. That
  judgement would need a user study or expert annotation.
- **30 scenarios is small.** They were chosen to cover the design's
  decision boundaries (sparse cells, conflicting constraints, budget
  edges), not to be a statistically powered sample.
- **The author wrote both the system and the labels.** The expectations
  were fixed before running, and disagreements are reported above, but
  this is not an independent evaluation.
- **Novelty and serendipity are not measured.** The dataset has no
  popularity or interaction signal, so there is no basis for computing
  them.
- **Prices are synthetic**, so budget compliance is verified against
  simulated prices. The logic is real; the price data is not.
